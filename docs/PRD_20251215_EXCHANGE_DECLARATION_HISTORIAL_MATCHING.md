# PRD: Exchange Declaration to Historial de Pagos Matching

## 1. Executive Summary

This feature automates the matching of Exchange Declarations (Declaraciones de Cambio) generated by Supra with Finkargo's Historial de Pagos (Payment History) records. When customers make payments through the online payment option, underlying dollar negotiations occur in Colombia that require formal declaration to the Banco de la Republica. While Supra generates these exchange declarations mapped to payments, customers need them mapped to the detailed payment applications (operations) that Finkargo maintains. This tool bridges that gap by intelligently matching exchange declarations from folder structures to grouped payment records.

## 2. Problem Statement

### Current Manual Process
1. Treasury team downloads "Historial de Pagos" from Finkargo platform
2. Downloads manual payments control sheet
3. Manually verifies matches between both files
4. Navigates through Supra's folder structure to find exchange declaration PDFs
5. Opens each PDF to extract the declaration number (field "4. Numero")
6. Manually maps declaration numbers to Historial de Pagos records
7. Fills in columns "Declaracion de Cambio Numero" and "DC Nombre" manually

### Key Challenges
- **One-to-Many Relationship**: A single payment may be applied to multiple operations, resulting in multiple Historial de Pagos rows for one exchange declaration
- **Tolerance Matching**: Dates may differ by a few days, amounts may differ by small decimals or dollars due to rounding
- **Folder Structure Navigation**: Exchange declarations are organized in a 3-level folder hierarchy (Customer > Date > Amount > PDF)
- **PDF Extraction**: Declaration numbers must be extracted from PDF content (field "4. Numero")
- **Format Variations**:
  - European number format (11.081,50) with periods for thousands and commas for decimals
  - Multiple date formats in folder names (DD-MM-YYYY and YYYYMMDD)

## 3. Goals & Success Metrics

### Goals

### 5.2 Matching Logic

#### Matching Algorithm
1. **Step 1 - Inventory Scan**: Scan the exchange declarations folder structure and extract:
   - Customer name (from Level 1 folder)
   - Declaration date (from Level 2 folder, formats: DD-MM-YYYY or YYYYMMDD)
   - Declaration amount (from Level 3 folder, European format: 11.081,50)
   - Declaration number (from PDF content, field "4. Numero")
   - PDF file path

2. **Step 2 - Historial Grouping**: Parse and group Historial de Pagos by:
   - Customer name (normalized)
   - Payment date (Fecha de pago column)
   - Sum of Capital amounts per group

3. **Step 3 - Fuzzy Matching**: For each declaration, find best matching payment group:
   - Customer name fuzzy match (normalized, removing SAS/LTDA/SA suffixes)
   - Date within tolerance (±N days)
   - Amount within tolerance (±$X or ±Y%)

4. **Step 4 - Assignment**: Assign declaration number and PDF path to all Historial de Pagos rows in the matched group

#### Matching Rules

| Rule | Description | Tolerance |
|------|-------------|-----------|
| Customer Name | Fuzzy match after normalization (case-insensitive, remove legal suffixes) | Levenshtein distance ≤ 3 or 90% similarity |
| Date | Match declaration date to payment date | ± 7 days (configurable) |
| Amount | Match declaration amount to sum of grouped Capital | ± $2.00 or ± 0.5% (configurable) |

#### Grouping Logic
Historial de Pagos records are grouped by:
1. **Primary Key**: (Cliente Normalized, Fecha de pago)
2. **Aggregation**: SUM(Capital) for each group
3. **Result**: One grouped record may contain multiple Historial rows (one-to-many)

## 8. Matching Algorithm

### 8.1 Algorithm Overview

```
INPUT:
  - declarations: List[DeclarationInventoryItem]  # From folder scan
  - payment_groups: List[PaymentGroup]            # From Historial grouping
  - config: MatchConfig (date_tolerance, amount_tolerance)

OUTPUT:
  - matches: List[MatchResult]

ALGORITHM:
1. Normalize all customer names
2. Build customer index for declarations (Dict[normalized_name, List[declarations]])
3. For each payment_group:
   a. Find candidate declarations by customer name (fuzzy match)
   b. Filter by date tolerance
   c. Filter by amount tolerance
   d. Score remaining candidates
   e. Select best match (highest score)
   f. If score > threshold: matched
      Else if partial match: partial
      Else: unmatched
4. Check for conflicts (same declaration matched to multiple groups)
5. Return all matches with status and confidence
```

### 8.2 Tolerance Handling

| Dimension | Default Tolerance | Rationale |
|-----------|-------------------|-----------|
| Date | ± 7 days | Banking processing delays, timezone differences |
| Amount | ± $2.00 or ± 0.5% | Rounding errors, exchange rate micro-fluctuations |

**Scoring Formula:**
```python
def calculate_match_score(payment_group, declaration, config):
    # Customer name score (0-40 points)
    name_score = fuzz.ratio(
        payment_group.customer_normalized,
        declaration.customer_normalized
    ) * 0.4

    # Date proximity score (0-30 points)
    date_diff = abs((payment_group.payment_date - declaration.declaration_date).days)
    date_score = max(0, 30 - (date_diff * 4))  # -4 points per day

    # Amount proximity score (0-30 points)
    amount_diff = abs(payment_group.total_capital - declaration.amount)
    amount_score = max(0, 30 - (amount_diff * 5))  # -5 points per dollar

    return name_score + date_score + amount_score  # Max: 100 points
```

### 8.3 Conflict Resolution

**Scenarios:**
1. **Multiple declarations for one payment group**: Select highest-scoring match, flag for review
2. **One declaration matches multiple payment groups**: Error - declarations are unique
3. **No match found**: Mark as unmatched, allow manual override

|----------|----------|
