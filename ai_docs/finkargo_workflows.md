## Contract Lifecycle Workflow

### Overview

The contract lifecycle involves two departments: **Operations** (requesters) and **Legal** (reviewers).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         CONTRACT LIFECYCLE                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   OPERATIONS                          LEGAL                                 │
│   ───────────                         ─────                                 │
│                                                                             │
│   1. Search Client ────────────►                                            │
│      by NIT                                                                 │
│                                                                             │
│   2. Request Contract ─────────► 3. Contract appears in                     │
│      (Select Type)                  Review Queue                            │
│                                                                             │
│                                  4. Review Contract                         │
│                                     - Preview content                       │
│                                     - Download DOCX                         │
│                                     - Approve/Reject                        │
│                                                                             │
│   5. Download Approved  ◄──────── (If Approved)                             │
│      PDF for signing                - PDF generated                         │
│                                     - Stored in Supabase                    │
│                                                                             │
│   6. Send to Client                                                         │
│      for signature                                                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Step-by-Step Process

#### Step 1: Operations - Search Client

**Location:** Operations Dashboard > Solicitar Contrato tab

**Actions:**
1. Enter client NIT in search field
2. System queries `/api/legal/clients/search?nit={nit}`
3. Client data displayed with company info and credit limit

**Frontend Component:** `FKContractRequest.tsx`, `FKOtrosiRequest.tsx`, or `FKInventarioRequest.tsx`

#### Step 2: Operations - Request Contract

**Contract Types:**

| Type | Tab | Special Requirements |
|------|-----|---------------------|
| Activos | "Solicitar Contrato Activos" | Client NIT only |
| Otrosí | "Solicitar Otrosí No. 1" | Client NIT only |
| Inventario Bodega | "Solicitar Inventario Bodega" | Client NIT + RUT PDF upload |

**API Call:** `POST /api/operations/contracts/generate`

```json
// Form data
{
  "client_nit": "900123456-1",
  "contract_type": "activos"  // or "otrosi", "inventario_bodega"
}
// For inventario_bodega, also includes rut_file
```

**Contract ID Generation:**
- System generates sequential ID: `{TYPE}-{YEAR}-{SEQUENCE}`
- Example: `ACT-2025-034`, `OTR-2025-015`, `INV-2025-003`

**Initial Status:** `under_review`

#### Step 3: Legal - Review Queue

**Location:** Legal Dashboard > Cola de Revisión tab

**Displayed Information:**
- Contract ID (e.g., ACT-2025-034)
- Contract Type
- Client NIT
- Company Name
- Credit Limit
- Generation Date
- Generated By

**Frontend Component:** `FKReviewQueue.tsx`

**API Call:** `GET /api/legal/contracts/pending-review`

#### Step 4: Legal - Review Contract

**Available Actions:**

1. **Preview** - View populated contract content
   - API: `GET /api/legal/contracts/{id}/preview`

2. **Download DOCX** - Edit template if needed
   - API: `GET /api/legal/contracts/{id}/download/docx`

3. **Approve** - Approve contract
   - Status changes to `approved`
   - PDF automatically generated and stored
   - API: `POST /api/legal/contracts/{id}/review` with `{"action": "approve"}`

4. **Reject** - Reject with notes
   - Status changes to `rejected`
   - Notes stored for Operations to see
   - API: `POST /api/legal/contracts/{id}/review` with `{"action": "reject", "notes": "..."}`

#### Step 5: Operations - Download Approved PDF

**Location:** Operations Dashboard > Contratos Aprobados tab

**Features:**
- Filter by contract type
- Sort by various fields
- Search by client name/NIT
- Date range filtering
- Credit limit range filtering

**Download:** Click download button to get approved PDF from Supabase Storage

**Frontend Component:** `FKApprovedContracts.tsx`

**API Call:** `GET /api/operations/contracts/{id}/download/pdf`

#### Step 6: Send to Client

Manual process outside the system - Operations emails PDF to client for physical or digital signature.

## Client Data Import Workflow

### Overview

Legal team can bulk import client data from CSV or Excel files.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       CLIENT DATA IMPORT                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   1. Prepare File ──────────► 2. Upload File ──────────► 3. Review Results  │
│      (CSV/Excel)                 (Drag & Drop)              (Success/Error) │
│                                                                             │
│   Template Formats:                                                         │
│   - Simple Template (direct columns)                                        │
│   - FinCargo Export (automatic mapping)                                     │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Required Columns (Simple Template)

| Column | Type | Required | Description |
|--------|------|----------|-------------|
| nit | string | Yes | Client NIT (tax ID) |
| nombre_importador | string | Yes | Company name |
| representante_legal | string | Yes | Legal representative |
| cedula_representante | string | Yes | Representative ID |
| ciudad_domicilio | string | Yes | City |
| cupo_plataforma | number | Yes | Credit limit |
| direccion_comercial | string | No | Business address |
| tipo_identificacion_representante | string | No | ID type (CC, CE, etc.) |
| nombre_contrato_marco | string | No | Master contract name |
| kam_nombre | string | No | Account manager name |
| kam_email | string | No | Account manager email |
| destinatario_nombre | string | No | Recipient name |
| destinatario_email | string | No | Recipient email |

### Import Process

1. **Upload File**
   - Drag & drop or click to select
   - Accepts: `.csv`, `.xlsx`, `.xls`

2. **Auto-Detection**
   - System detects template format
   - Maps columns automatically

3. **Bulk Upsert**
   - New clients inserted
   - Existing clients (by NIT) updated

4. **Results Summary**
   - Total processed
   - Successful imports
   - Failed imports with error details

**Frontend Component:** `FKClientDataImport.tsx`

**API Call:** `POST /api/legal/clients/import` (multipart/form-data)

## Mexico Invoicing Automation Workflow

### Overview

Finance team processes Mexico invoicing data and generates ZIP packages with PDFs/XMLs.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    MEXICO INVOICING AUTOMATION                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   1. Upload Excel ─────► 2. Drive Sync ─────► 3. Search/Filter              │
│      (Master File)         (32 columns)         (invoices)                  │
│                                                                             │
│                                              ▼                              │
│                                                                             │
│   4. Generate ZIP ◄────────────────────────────                             │
│      - PDFs folder                                                          │
│      - XMLs folder                                                          │
│      - Excel report                                                         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Step-by-Step Process

#### Step 1: Upload Excel

**Location:** Finance > Reportería Automática MX

**Required Columns:**
- UUID
- CODIGO DE OPERACIÓN
- Conceptos
- Fecha emision
- RFC receptor
- Razon receptor
- SubTotal
- IVA Trasladado
- IVA Exento
- Total

**Frontend Component:** `FKExcelUploader.tsx`

**API Call:** `POST /api/finance/upload-excel`

#### Step 2: Google Drive Sync

Automatic process during upload:
1. Read uploaded Excel (32 columns)
2. Download master Excel from Google Drive (if exists)
3. Merge data (new records added, existing updated)
4. Upload merged data back to Drive

**Sync Statistics Returned:**
- `new`: New records added
- `updated`: Existing records updated
- `unchanged`: Records without changes

#### Step 3: Search and Filter

**Search Types:**
- By Operation Code (partial match, comma-separated)
- By RFC Receptor (exact match)

**Optional Date Filters:**
- Fecha Inicio (start date)
- Fecha Fin (end date)

**Combined Filters:** Can combine operation code/RFC with date range.

**API Call:** `POST /api/finance/search`

#### Step 4: Generate ZIP Package

**Contents:**
1. `PDFs/` - Invoice PDF documents
2. `XMLs/` - Invoice XML files
3. `Reporte_Facturas_{date}.xlsx` - Detailed Excel report

**File Naming:**
- With operation code: `Facturacion_MX_{codigo}_{date}.zip`
- Without: `Facturacion_MX_{date}.zip`

**API Call:** `POST /api/finance/generate-zip`

## RUT Document Parsing Workflow

### Overview

For Inventario Bodega contracts, the system parses RUT (Colombian tax ID) PDF documents to extract custodian information.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        RUT PARSING                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   1. Upload RUT PDF ────► 2. Parse with PyMuPDF ────► 3. Extract Fields     │
│      (Max 5MB)              (Text extraction)           (Custodian data)    │
│                                                                             │
│   Extracted Fields:                                                         │
│   - nombre_operador_custodio                                                │
│   - ciudad_domicilio_custodio                                               │
│   - nit_operador_custodio                                                   │
│   - nombre_representante_legal_custodio                                     │
│   - email_operador_custodio                                                 │
│   - cc_representante_legal_custodio                                         │
│   - tipo_identificacion_representante_legal_custodio                        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Process

1. **Upload Validation**
   - Must be PDF (`application/pdf`)
   - Max 5MB size

2. **Text Extraction**
   - Uses PyMuPDF (fitz) library
   - Handles columnar and standard layouts

3. **Field Mapping**
   - Regex patterns extract specific fields
   - Handles various RUT formats (GAMALOG, standard)

4. **Data Integration**
   - Extracted data added to contract `data_snapshot`
   - Used to populate Inventario Bodega template

**Backend Service:** `RUTParserService` (`backend/src/core/servicios/rut_parser_service.py`)

## Authentication Flow

### Login Process

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         LOGIN FLOW                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   1. User enters ────► 2. Supabase Auth ────► 3. JWT Token                  │
│      credentials          validates              returned                   │
│                                                                             │
│                                              ▼                              │
│                                                                             │
│   4. AuthContext ────► 5. Fetch user_profiles ────► 6. Profile Cached       │
│      stores session       (role, permissions)          (5 min TTL)          │
│                                                                             │
│                                              ▼                              │
│                                                                             │
│   7. Redirect to ────► 8. Role-based UI                                     │
│      appropriate           rendered                                         │
│      dashboard                                                              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Session Management

1. **Token Storage** - JWT stored in localStorage by Supabase
2. **Profile Caching** - User profile cached for 5 minutes
3. **Periodic Validation** - Session validated every 5 minutes
4. **Focus Validation** - Session validated when window regains focus
5. **Token Refresh** - Handled automatically by Supabase

### Role-Based Routing

| Role | Default Route | Accessible Routes |
|------|---------------|-------------------|
| admin | / | All routes |
| legal | /department/legal | Legal dashboard, client management |
| operations | /operations/contratos-colombia | Operations dashboards |
| cliente | /client | Client dashboard only |

## Document Generation Workflow

### Overview

When a contract is approved, the system generates and stores a PDF.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    DOCUMENT GENERATION                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   1. Get Template ────► 2. Populate ────► 3. Generate ────► 4. Convert      │
│      (.docx file)         Placeholders      DOCX            to PDF          │
│                                                                             │
│                                                          ▼                  │
│                                                                             │
│   5. Upload to Supabase Storage ────► 6. Store URL in contract record       │
│      (approved-contracts bucket)                                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Template Placeholders

The DOCX templates contain placeholders that get replaced:

| Placeholder | Data Source |
|-------------|-------------|
| `{{IMPORTER_NAME}}` | `data_snapshot.nombre_importador` |
| `{{TAX_ID}}` | `data_snapshot.nit` |
| `{{LEGAL_REP_NAME}}` | `data_snapshot.representante_legal` |
| `{{LEGAL_REP_ID}}` | `data_snapshot.cedula_representante` |
| `{{CITY}}` | `data_snapshot.ciudad_domicilio` |
| `{{CREDIT_LIMIT}}` | `data_snapshot.cupo_plataforma` (formatted) |
| `{{CONTRACT_ID}}` | `data_snapshot.contract_id` |
| `{{GENERATION_DATE}}` | `data_snapshot.generation_date` |

### Storage Structure

```
Supabase Storage
└── approved-contracts/
    ├── {contract_uuid}_approved.pdf
    ├── {contract_uuid}_approved.pdf
    └── ...
```

**Backend Service:** `DocumentService` (`backend/src/core/servicios/document_service.py`)

## Error Handling Patterns

### Frontend Error Handling

```typescript
try {
  const result = await legalService.searchClients({ nit: searchNit });
  setClients(result);
} catch (error) {
  const errorMessage = error?.response?.data?.detail || 'Error al buscar clientes';
  setError(errorMessage);
}
```

### Backend Error Responses

```python
# Validation Error
raise HTTPException(status_code=400, detail="Invalid contract type")

# Not Found
raise HTTPException(status_code=404, detail=f"Client with NIT {nit} not found")

# Authorization Error
raise HTTPException(status_code=403, detail="Access denied. Required roles: legal")

# Server Error
raise HTTPException(status_code=500, detail=f"Error generating document: {str(e)}")
```

## Data Snapshot Pattern

When a contract is generated, client data is "snapshotted" to preserve the state at generation time:

```json
{
  "data_snapshot": {
    "nit": "900123456-1",
    "nombre_importador": "EMPRESA S.A.S.",
    "representante_legal": "Juan Pérez",
    "cedula_representante": "1234567890",
    "ciudad_domicilio": "Bogotá",
    "cupo_plataforma": 50000000,
    "contract_id": "ACT-2025-034",
    "contract_type": "activos",
    "generation_date": "2025-01-15",
    // For inventario_bodega:
    "nombre_operador_custodio": "CUSTODIO S.A.",
    "nit_operador_custodio": "800456789-1"
  }
}
```

This ensures:
1. Historical accuracy - contract shows data at generation time
2. Audit trail - changes to client data don't affect existing contracts
3. Template population - all data needed for document generation
